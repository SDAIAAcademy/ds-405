Columnar files

A query that needs three columns should read three columns

A row file (CSV)

Every row is read whole to find three fields in it. Types are guessed on every read.

A column file (Parquet)

Each column is stored apart, typed and compressed, with statistics per block, so a reader skips columns and blocks it does not need.

Partitions add a third skip: whole files, by the values in the folder names.

Ask the room what the three skips are: columns (projection), blocks inside a file (statistics), files (partitions). The lab measures what they are worth on this lake.

Incremental and idempotent loads

Real schedules

Every load will run twice one day

Retry

The load wrote, then failed before saying "done"; the scheduler runs it again.

Re-delivery

Ufuq sends 2026-01-03 again with 20 values corrected.

Sidra's 2026-01-05 file corrects 15 results of 2026-01-02.

Lab 2.2 · step 2

"Same table" means same content, in any order and any files

def table_hash(df):
    d = df.select(COLS).sort(KEY)          # fixed columns, fixed order
    return hashlib.sha256(d.write_csv().encode()).hexdigest()[:16]

Same fingerprint, same rows: the proof that a re-run day gives identical output.

Leave out columns that legitimately change between runs (a load timestamp). Here the delivered_day is left out because a re-sent day keeps its date anyway. U.fingerprint in the helper does the same with column hashes, faster on big tables.

Lab 2.2 · step 3

Overwrite the day's partition: a re-run replaces, never adds

df.write_delta(table, mode="overwrite",
    delta_write_options={"predicate": f"delivered_day = '{day}'",
                         "partition_by": ["delivered_day"]})
Its limit. Days 1 to 5 by overwrite: 299,991 rows, 15 duplicate keys: Sidra's corrections landed in day 5's partition, the originals stayed in day 2's.

Delta Lake's overwrite with a predicate rewrites only the matching rows in one atomic commit. Ufuq's re-sent day is handled: the newer file replaces the day.

Lab 2.2 · step 4

Merge on the business key: corrections replace what they correct

DeltaTable(table).merge(df.to_arrow(),
    predicate="t.encounter_id = s.encounter_id AND t.test_code = s.test_code "
              "AND t.result_seq = s.result_seq",
    source_alias="s", target_alias="t") \
  .when_matched_update_all().when_not_matched_insert_all().execute()

Days 1 to 5 by merge: 299,976 rows, 0 duplicate keys.

The business key is what the producer means by "the same result": encounter, test and round. A key that is too narrow merges different results; too wide, and corrections insert instead of update. The contract should name the key.

Lab 2.2 · step 5

The proof: every day loaded twice gives the same fingerprint

oncedays 1, 2, 3, 4, 5 → fa71c591dcabaeb1
twicedays 1 to 5, again 1 to 5, and day 3 a third time → fa71c591dcabaeb1

Order still matters. Replaying day 2 after day 5 puts the old values back until day 5 is replayed. Real pipelines compare a delivery version before updating.

Full-size fingerprints. In the twice-run, the second pass over day 2 reverts Sidra's corrections and the second pass over day 5 restores them. A when_matched_update conditioned on a delivery sequence number fixes it: a good capstone refinement.

One simulated day of a 480,000-line table: 4,416 inserts, 1,891 updates, 129 deletes.

Contrast: Rawdah's ward reference table, 1,840 rows copied weekly with about 12 changes, is simply reloaded.

Ask the room to choose first. The reload reads about 7,190 times what changed. The updated-at query misses deletes (a deleted row carries no new time) and 123 intermediate states. The log holds every committed change in order. Read the log when copies are frequent and changes few; reload what is small or rare, and after a gap in the log. Numbers: the day2_examples script. Source: Debezium features page; the course does not install it.

Reading the change log

Apply events in log order, merged on the key, and remember the last one applied

seq 66insert line 480047 (copy 3)

Applied with the merge of Lab 2.2: insert, update or delete by key, skipping any event at or below the sequence already applied, so a replay changes nothing.

One line from the same simulated day. Order by log position, never by arrival. The last applied sequence makes the apply idempotent. A reader stopped longer than the log is kept loses events: take one full snapshot and resume from its position.

Dr. Fadwa Al-Qassabi's question is every release's reproducibility promise. Lab 2.3 builds the four-version table from the lake.

Open table formats

A table format adds a log of commits to files: every commit is a version

Delta Lake

A JSON log beside the Parquet files. Used in the labs through delta-rs: no Java needed.

Apache Iceberg

Snapshots with metadata files; time travel by snapshot id.

DuckLake

The catalog in a SQL database; snapshots and time travel.

Same ideas in all three: atomic commits, versions, time travel, schema evolution.

Interchangeable examples of the slot. From each project's site: DuckLake keeps its metadata in a SQL database (PostgreSQL, MySQL, SQLite or DuckDB); Iceberg time-travels with FOR VERSION AS OF a snapshot id. Check versions before the cohort.

Written, but not found

A file in the table's folder is not a file in the table

Three months committed, then a January file copied in without a commit. A table's readers read only the files its log lists; a glob reads the folder, hence "but the data is there". Numbers: the day2_examples script. Source: the Delta transaction log protocol.

Diagnose, then register

Compare what the metadata lists with what the folder holds

What you findRegister it by
Files copied in, or a job that stopped before its commit (a table format such as Delta)Writing the rows through the table's writer, so a commit lists them
A new folder the catalog has no partition for (a Hive-style catalog)ALTER TABLE … ADD PARTITION, or MSCK REPAIR TABLE for every new folder
month=2026-1 beside month=2026-01Fixing the writer's format: a filter on 2026-01 finds none of its rows

Check the folder against the metadata first, then the partition value's spelling. Spark's documentation: partitions of a table created over existing data are not registered automatically; REPAIR TABLE adds them, ALTER TABLE ADD PARTITION adds one, and both clear the table's cached data. The misspelt folder is computed by the day2_examples script. Lab 2.3 ends with a stretch question on this.

A lineage event says which run read what and wrote what

{"eventType": "FAIL",

OpenLineage's object model: run events (START, then COMPLETE or FAIL) naming a job, a run and its input and output datasets, with facets for anything else.
